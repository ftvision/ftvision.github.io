On June 30, 2026, Anthropic released a new product: Claude Science<Reference id="official-claude-science" citation="Anthropic, Claude Science, an AI workbench for scientists, June 30, 2026." url="https://www.anthropic.com/news/claude-science-ai-workbench" />. It looks like a simple local app.<Marginnote>Starting the app unexpectedly opens a localhost page in your browser instead of a conventional desktop window.</Marginnote> Its real novelty sits below the interface: Anthropic has turned the scientific workbench itself into an agent harness, with a daemon mediating the path from a running analysis to the evidence behind the final artifact.

The visible experience is intentionally familiar. You open a project, talk to an agent, watch it write and execute code, and receive a figure, table, structure, or report. Each artifact also exposes the code that produced it. That code was my first way into the architecture. In one generated analysis, I found a call like this:

```python
try:
    EMAIL = host.get_user_email()
except Exception:
    EMAIL = None
```

There was no `import host`. There was no `host` package in the Python environment. Yet the name existed inside the running kernel. A starter project contained another clue, `host.exec_peek(...)`, inside the recorded code path. These are small anomalies in an otherwise ordinary-looking Python session, but they invite curious people to investigate: **what put `host` there, and what is on the other side of the call?**<LocalSource id="artifact-host-clue" source="~/.claude-science/orgs/<org-id>/operon-cli.db, artifact_versions.extracted_code; ~/.claude-science/runtime/<version>/seed/manifest_*.json" note="Generated artifact code and bundled starter-session code containing host calls" />.

Following that question reveals more of the product. The readable `kernel_worker.py` under `~/.claude-science/runtime/<version>` says that the host SDK is installed through the first `execute()` after kernel startup. The SDK itself is not a normal file in that runtime. It is embedded as Python source inside the staged `claude-science` daemon, alongside the TypeScript/JavaScript host implementation. Extracting the daemon with `strings` reveals how the fragments are selected, injected, and attached to one singleton; it also reveals that methods such as `host.llm()` and `host.mcp()` are synchronous RPC back into the daemon, not privileged work performed by the Python process.

That boundary is an architectural design. Python and R can keep large datasets and fitted analytical models alive for hours, while the daemon retains authority over connectors, models, credentials, remote compute, verification, and publication. The agent uses code as a compact orchestration language, but the code runs inside capability-shaped environments. A reviewer inspects the work without becoming part of the main agent's self-reflection loop. An artifact survives the conversation with its producing code, environment, dependencies, and verification record still attached.

For Agent Harness developers, Claude Science is a useful case study: it shows how a model's raw capability, the harness that governs it, and the application's own execution environment combine to turn a scientist's scattered work steps into one connected pipeline. This essay traces how it does that: first the app shell and the payload it places on disk, then the hidden boundary behind `host`, then the execution, artifact, and verification flows that boundary makes possible. The implementation examined here is `0.1.15`.<Marginnote>The mechanism claims come from the local app bundle, files under `~/.claude-science/runtime`, SQLite migrations, and Python or daemon fragments extracted from `~/.claude-science/bin/claude-science` with `strings`.</Marginnote>

## Following `host` Into the Daemon

The artifact code panel gives me the first clue, but the runtime explains how the trick is performed. Near kernel startup, `kernel_worker.py` initializes an ordinary persistent namespace and leaves this comment:

```python
# The host SDK (host.lineage/query/llm) is installed via the first
# execute() after kernel start -- see base.ts postStartCode mechanism.
```

The file contains protocol plumbing for SDK calls, but not the SDK implementation itself<LocalSource id="kernel-injection-clue" source="~/.claude-science/runtime/<version>/kernels/kernel_worker.py, near the kernel namespace initialization" note="The shipped Python worker identifies the first-execute postStartCode injection mechanism" />. To find the missing source, the next step is the staged daemon:

```bash
strings ~/.claude-science/bin/claude-science > claude-science.strings
rg -n 'FRAGMENT MODEL|Host-callback protocol|class _OperonSDK' claude-science.strings
```

The recovered Python says that one base fragment is always sent and that gated fragments are concatenated afterward according to the agent profile. Those later fragments attach methods to an already-created singleton. The base fragment binds that singleton to both `host` and the legacy name `operon`, then registers the object in `sys.modules`, which is why `import host` also appears to work even though no module was installed.

The same fragment answers what happens on the other side of a method call. Inside a kernel, `host.llm()`, `host.artifacts()`, `host.mcp()`, and `host.compute.create()` look like ordinary Python. Each ultimately serializes a synchronous request over the private kernel protocol and waits for a matching daemon response:

<HostCallProtocol />

The injected method surface is a usability aid, not the final authority. The daemon chooses an allowed method set for each kernel kind, checks that permit before dispatch, and lets individual handlers perform their own validation. A fabricated raw `_host_call("mcp", ...)` does not recover a capability that was omitted from the analysis kernel<LocalSource id="host-rpc" source="Embedded Python and host dispatcher in ~/.claude-science/bin/claude-science; extract with strings and search for 'Host-callback protocol', '_host_call', and 'Host call not permitted'" note="SDK fragment assembly, host-call wire protocol, daemon permit sets, and dispatcher gate" />.

<Blockquote variant="pullquote">
  Kernels hold working state. The daemon holds authority and history.
</Blockquote>

The daemon is the architectural center. It owns identity, permissions, agent frames, execution records, artifact storage, connector access, compute providers, verification state, and the local web service. Python, R, shell processes, the stdlib-only control REPL, and remote compute remain subordinate workers. They can calculate, retain state, and produce files; they do not decide which external capabilities they may use or which outputs become durable.

## Cut I: Code as the Orchestration Language

Most agent products follow a Re-Act loop with modification: a paragraph of reasoning, one or more tool calls, a group of results, then next turn. Claude Science does the same, but its distinction is to use python code to express and orchestrate tool-call control flows, and the difference is easiest to see at scale.

Take the literature sweep behind its shipped `literature-review` skill. The skill loads helpers like `search_openalex` and `expand_citations` straight into the Python kernel; one cell uses them to pull hundreds of candidate papers and walk their citation graph in both directions, and the whole set stays in the kernel as a table. Because model calls run inside that same kernel, a loop can put `host.llm()` on each candidate, scoring relevance and extracting the effect it reports, so a triage over hundreds of records is one Python cell rather than hundreds of turns. Then matplotlib draws the result. In the model's transcript, that entire sweep is a couple of tool calls, not the hundreds a turn-by-turn tool loop would spend<LocalSource id="literature-sweep" source="~/.claude-science/runtime/<version>/skills/literature-review/kernel.py and SKILL.md; ~/.claude-science/runtime/<version>/mcp-servers/bio-tools/lib/openalex_works" note="Shipped literature-review skill: kernel-loaded search_openalex and expand_citations, plus in-kernel model calls over retrieved records" />.

Here are two important points. First, the papers never have to enter the model's context. They live as data inside the persistent kernel, and only the compact synthesis crosses back. Second, the iteration lives in the code, not in the model's turn-by-turn transcript. One `for` loop makes its N calls from inside a single cell, so the model writes the cell once and reads a single result. A discrete tool interface would instead spend N separate tool-call and result exchanges, a full model turn apiece. Code moves the loop out of the language model.

Code is therefore not just a way to analyze returned data. **It compress the orchestration.** The rest of this cut is the machinery that keeps that compression safe: the code runs inside capability-shaped processes, and the boundaries between them are as deliberate as the code itself.

Results are serialized into `./handoff/<name>.json`, then loaded by an analysis kernel. ### The control kernel and the data kernels

The control REPL runs Python in isolated, stdlib-only mode. It receives orchestration fragments for MCP, agents, skills, frame queries, delegation, structured output, and remote compute. The package-rich Python and R kernels do not receive those surfaces. They receive analysis-oriented methods such as artifact lookup, lineage, model calls, credentials, and analytic libraries.

When analysis code tries `host.mcp`, the SDK does not pretend the method exists. Its `AttributeError` says that connector tools have no surface in that kernel, tells the agent to fetch in `repl`, write JSON under `./handoff`, and read it from Python. The same teaching error covers agents, skills, compute, query, frames, execution control, and structured output. It also names the process boundary: the kernels share a workspace current directory, but not LLM context or memory<LocalSource id="control-data-contract" source="Embedded SDK in ~/.claude-science/bin/claude-science; extract with strings and search for 'no surface in this kernel' and 'host.mcp'" note="User-facing control/data-kernel contract and control-only MCP fragment" />.

| Host surface                           | Analysis Python/R | Operon control REPL    | Reviewer          |
| -------------------------------------- | ----------------- | ---------------------- | ----------------- |
| artifacts, lineage, model calls        | yes               | yes                    | read-only subset  |
| MCP, agents, skills                    | no                | yes                    | no                |
| compute, delegation, output submission | no                | profile/provider gated | no                |
| frame and database introspection       | no                | yes                    | bounded read-only |

The missing SDK methods are only the first gate. Fragment absence teaches the API and produces a useful error. The daemon permit set is authority. Even if kernel code manufactured a raw `_host_call("mcp", ...)`, the analysis permit set excludes it and the MCP handler independently requires an Operon kernel, authentication, connector resolution, schema validation, and policy approval<LocalSource id="daemon-gates" source="Host dispatcher in ~/.claude-science/bin/claude-science; extract with strings and search for 'Host call not permitted', 'MCP calls require an Operon kernel', and 'validateToolInput'" note="Daemon-side host-call gates and MCP validation path" />.

The same split shows up at smaller scale: a list comprehension can call a connector once per record and stay one REPL tool use with N daemon round trips.

Code is also a capability boundary. Third-party scientific packages run in stateful analysis kernels. Connector access and agent mutation run in the narrower control kernel. A pandas object cannot leak by reference from Python into `repl`; it must become a file. It also makes the crossing nameable, inspectable, hashable, and eligible for artifact lineage.

### Persistent state without kernel authority

The Python worker is a long-lived subprocess with a persistent namespace. It accepts JSON requests, compiles each cell under a synthetic filename such as `<kernel:17>`, registers source in `linecache`, and evaluates it in the same namespace used by earlier cells. A loaded matrix, fitted model, or helper function can survive across turns. Each response includes stdout, stderr, trace information, wall time, CPU time, and peak memory<LocalSource id="python-worker" source="~/.claude-science/runtime/<version>/kernels/kernel_worker.py" note="Long-lived Python worker, persistent source registration, interrupt survival, and per-cell usage" />.

Persistence comes with protocol hardening. Streaming output, final responses, and mid-cell host calls share locks so JSON lines cannot interleave. Protocol file descriptors are separated from user-visible stdout. Secret variables are removed before user code runs. Dynamic-library loads from writable roots are refused unless they fall under an explicit environment exemption. `exit`, `quit`, and interrupts are handled without casually destroying the kernel.

R mirrors the same broad shape. It is a long-lived `Rscript` worker that retains `.GlobalEnv`, exchanges JSON over standard streams, strips secrets, guards `dyn.load`, and supports host callbacks during evaluation. 

Bash is different: the evidence points to managed subprocess execution rather than persistent shell memory. It still participates through execution records, background output, process-group interruption, and host approvals<LocalSource id="r-shell-workers" source="Embedded R worker and shell runner in ~/.claude-science/bin/claude-science; extract with strings and search for '.GlobalEnv', 'dyn.load', and 'process group'" note="Persistent R worker and the bounded evidence for process-based shell execution" />.<Marginnote>Python and R persistence are explicit in worker source. Shell persistence is not. On macOS, the extracted write-trace configuration also says the Darwin path does not trace Bash in the same way as Linux.</Marginnote>

Persistent kernels are not new. The design choice that matters here is persistence without kernel authority. A Python process may hold a giant matrix for an hour; it must still ask the daemon for a privileged host operation.

### Agent-swarm orchestration in Code

The control plane does not stop at compute. Its gated SDK fragments expose agent-profile CRUD, skill and connector attachment, skill editing and publication, child delegation, collection, interruption, and structured result submission. These are host calls, not edits to an informal prompt file. The daemon can apply validation and policy to the construction of new agents as well as to their tool use<LocalSource id="agent-surface" source="Embedded SDK and host handlers in ~/.claude-science/bin/claude-science; search extracted strings for 'host.agents', 'host.skills', 'delegate', and 'submit_output'" note="Daemon-mediated agent, skill, delegation, and structured-output surfaces" />.

Onboarding uses the same runner in a deliberately narrow form. The shipped `ONBOARDING` profile cannot run Python, R, Bash, `repl`, search, package management, or remote compute. It conducts a bounded interview with option cards, collects permissions after a first task is selected, and hands the task to a working agent. A product flow that could have been a fixed wizard becomes a constrained agent profile inside the harness<LocalSource id="onboarding-agent" source="~/.claude-science/runtime/<version>/agents/onboarding/metadata.yaml" note="Constrained onboarding profile, question flow, permission timing, and handoff" />.

For harness developers, Cut I yields a specific lesson. Giving a model "code execution" is not one capability. Claude Science decomposes it into persistent data state, stdlib control code, external-tool RPC, managed subprocesses, remote jobs, and daemon-owned policy. Code joins those pieces without erasing their boundaries.

## Cut II: Artifacts, Not Messages, Are the Product

The `OPERON` prompt tells the agent to produce artifacts, not just answers. Workspace files are invisible to the user until saved. Figures should be embedded by version id. Reports should link artifacts by identity rather than ambiguous filename. The final response should point to the primary deliverable while the artifact tray carries the rest<LocalSource id="artifact-contract" source="~/.claude-science/runtime/<version>/agents/operon/metadata.yaml, 'Artifacts' instructions" note="OPERON's artifact-first user-output contract" />.

This is not presentation polish. It names the system's durable unit.

For that record to be useful, it has to answer one question: what each version was built from. Claude Science answers with a dependency graph over exact versions, not filenames. What matters is not only the edges but how each one is known: some inputs are observed while the code runs, some are reconstructed after the fact, and a few stay pending until extraction settles. The figure puts that distinction first, and the rest of this cut is how each layer underneath it is recorded.

### Lineage is observed before it is reconstructed

Code text alone is a poor lineage oracle. A path may be assembled dynamically. A dataframe may be sliced through library calls. A figure may be written by an object whose origin is invisible in the final `savefig` statement. Claude Science first tries to observe dataflow while code runs.

Before agent's analytical code, the analysis SDK wraps selected readers and writers. Readers such as `pandas.read_*`, `numpy.load*`, and `anndata.read_h5ad` attach source version ids to returned objects. Writers such as `DataFrame.to_*`, `Figure.savefig`, `numpy.save*`, and `json.dump` harvest those tags and record which source versions reached an output path. When that path becomes an artifact, the host asks the kernel for its runtime inputs<LocalSource id="runtime-provenance" source="Runtime-provenance fragment embedded in ~/.claude-science/bin/claude-science; search extracted strings for '__operon_runtime_inputs__'" note="Runtime reader/writer wrapping, object tags, and host harvest surface" />.

```text
artifact version id
  -> tagged reader result
  -> pandas / NumPy transformations
  -> wrapped writer(output_path)
  -> __operon_runtime_inputs__(output_path)
  -> exact upstream version edge
```

The mechanism propagates tags through pandas attributes, tagged NumPy subclasses, scalar wrappers, and a side table where possible. It is deliberately not universal taint tracking. Its own non-goals include generic dataflow tracing and complete R or Bash coverage. Plain dictionaries, unsupported libraries, and executed strings can lose tags. If a writer fires with tags, the host has a direct mapping. If not, the host falls back to code and dependency reconstruction.

That ordering is the important choice:

```text
runtime observation when tags survive
  -> recorded reads, writes, executions, and host calls
  -> post-hoc dependency mapping when direct evidence is incomplete
  -> pending / unresolved lineage when convergence has not finished
```


How about using LLM as a judge and ask an LLM to infer every edge from code? Claude Science does that as well, but only as a fallback<LocalSource id="provenance-fallback" source="Runtime-provenance and dependency-mapping code embedded in ~/.claude-science/bin/claude-science; search extracted strings for 'NOT a generic dataflow tracer' and 'dependency_mappings'" note="Explicit provenance non-goals and daemon-side dependency convergence" />.<Marginnote>Provenance confidence is uneven. Python has the richest object wrappers. R and Bash depend more on write tracing and post-hoc reconstruction, and the extracted Darwin configuration says Bash is not traced through the same preload path as Linux. "Has lineage" should not be presented as a binary guarantee.</Marginnote>

### The record beneath the file

An artifact is not merely a path. It is a project-scoped record with versions. The artifact row identifies project, root conversation, producing frame, filename, latest version, folder, priority, and whether the item is ephemeral or user supplied. Each version can preserve content type, size, checksum, storage path, extracted code, a code description, lineage messages, agent, language, dependency mappings, environment snapshot, annotations, and parent version. Separate rows store exact version-to-version dependencies<LocalSource id="artifact-schema" source="~/.claude-science/runtime/<version>/drizzle/sqlite/0000_yummy_ken_ellis.sql; 0004_content_snapshots.sql; 0005_execution_log.sql" note="Artifact identity, version metadata, dependencies, snapshots, and producing-cell fields" />.

Beneath that record, Claude Science records at least three evidence layers.

**First is the execution log.** A cell can record its frame, index, kernel id, environment, language, source, stdout, stderr, status, files written, files read, and error location. An artifact version can point back to the producing cell and to cell-source snapshots<LocalSource id="execution-log" source="~/.claude-science/runtime/<version>/drizzle/sqlite/0005_execution_log.sql; ~/.claude-science/orgs/<org-id>/operon-cli.db, execution_log and content_snapshots" note="Per-cell execution evidence and producing-cell links" />.

**Second is the host-call log.** A privileged call made inside a cell can be stored with method, arguments, sequence number, derivability, inline or referenced response data, error, byte count, and execution-log id. This separates "the code ran" from "the code asked the host for an external or privileged result"<LocalSource id="host-call-log" source="~/.claude-science/runtime/<version>/drizzle/sqlite/0006_host_call_log.sql; ~/.claude-science/orgs/<org-id>/operon-cli.db, host_call_log" note="Ordered host-call records linked to an execution" />.

**Third is the artifact graph.** Dependencies connect exact versions, not filenames. `host.lineage.graph(version_id)` returns topology cheaply; `host.lineage[version_id]` can return code, messages, environment, inputs, checksums, frames, and producing cells for a selected node. Together, these layers can represent: this figure came from that table, produced by this cell, after these host calls, under this environment, in this agent frame. Coverage may be incomplete, but the schema treats the chain as first-class state rather than a paragraph improvised after the fact.

### How code is reconstructed behind an artifact

There is no single magical "reconstruct code" function. The system assembles several evidence lanes.

If an artifact was saved directly from a recorded cell, `producing_cell_id` and cell sources provide the strongest path. For a more complex sequence, a version can store `extracted_code`, `code_description`, `lineage_messages`, and `dependency_mappings`. Environment and lineage snapshots can be addressed by hash. `parent_version_id` preserves ancestry. Runtime tags may provide exact upstream ids. The daemon then converges mappings into dependency edges while checking that stored mapping text has not changed under a concurrent update.

The result is a hierarchy of confidence:

1. observed runtime input tags and exact producing cells;
2. recorded files read or written and recorded host calls;
3. extracted code and environment snapshots;
4. post-hoc dependency mappings and descriptions;
5. unresolved or pending extraction.

That hierarchy belongs in the product explanation. Some edges were observed. Some were reconstructed. Some remain unsettled.

### Replay without pretending the host never existed

Export creates a difficult problem. Notebook code may contain `host.llm()`, `host.artifacts()`, `host.lineage`, `host.mcp()`, delegation, or app calls. Outside Claude Science, `host` is not an installed package and daemon state is absent. Exporting only Python would produce a notebook whose important calls fail.

The shipped replay shim chooses a direct solution. Host responses are written to `operon_tape.json`. A standalone notebook loads the tape, binds both `host` and the legacy `operon` name to a replay object, and consumes entries sequentially. Known discovery calls may be skipped when extracted code omits them. A method mismatch raises before the cursor advances, preventing one divergence from silently shifting every later response<LocalSource id="replay-shim" source="Notebook replay shim embedded in ~/.claude-science/bin/claude-science; search extracted strings for 'operon_tape.json' and 'host-SDK replay drift'" note="Sequential response tape, replay cursor, mirrored host surfaces, and unavailable capabilities" />.

The cursor logic is intentionally strict:

```python
rec = tape[self._i]
j = self._i
while rec["method"] != requested and rec["method"] in SKIPPABLE:
    j += 1
    rec = tape[j]
if rec["method"] != requested:
    raise RuntimeError("host-SDK replay drift")
# Only a match commits the cursor.
```

The shim mirrors model calls, artifacts, lineage, credentials, frames, children, delegation, MCP, and app tools. Its capability report admits that agents, skills, compute, and background execution controls are unavailable. Reordering calls or adding new host effects breaks the tape.

This is portability, not full recomputation. A replayed LLM answer is the answer recorded during the live run. A replayed MCP result is not a fresh query. The tape proves that exported code can execute against preserved host responses in the recorded order. It does not prove that a clean environment can regenerate those responses from the outside world. Nevertheless, Claude Science exports those dependencies as data, and the research process is kept as reproducible as possible <Marginnote>A synthetic smoke test confirmed sequential consumption, controlled skipping of a discovery entry, and soft handling of a recorded credential failure. No real exported notebook bundle was present in the inspected app data, so end-to-end export completeness remains unverified.</Marginnote>.

## Cut III: A Reviewer Outside the Main Agent Loop

LLM still hallucinates and makes mistakes. Many agent products try to mitigate this problem. A simple idea is to ask the same model that writes a result, reflects on it, and decides whether the reflection was sufficient. Even when a second model is called, the main loop often owns when to call it and what to do with the answer.

Claude Science implements differently: a detached verifier owned by the runner.

The target release ships two verification profiles, `REVIEWER` and `BOOKMARKER`. They are not two constantly running agents. The reviewer path is active in the observed local runtime. The bookmarker implementation ships in the same release, but `bookmarks_enabled` defaults to false, and no local bookmarker frame or transcript annotation was observed.

### What the reviewer is told to do

`REVIEWER` is not a second scientist. Its job is to read main agent's transcript and report where the work fabricated a result, hallucinated a source, or drifted from the plan, and its prompt is unusually strict about method. Its first rule is **trace, don't recompute**: if the agent claims a number, the reviewer finds the cell that printed it and looks for a contradiction, and a value it cannot trace inside its window is not, on its own, a finding. This targets a specific verifier failure. Two independent analyses can disagree because they chose different filters, libraries, or random seeds, and that disagreement alone does not show which one followed the user's work. A tracing reviewer asks: does the durable claim agree with the evidence path the session says produced it? To hold it to that question, the profile strips the tools that would let it wander off and start its own analysis. It disables planning, delegation, web search, and thinking, and it excludes Python, R, Bash, package and environment management, artifact writing, file editing, full-text retrieval, and compute. The daemon then grants only a read-only host surface: frames, scoped queries, artifact paths and listings, and lineage<LocalSource id="reviewer-profile" source="~/.claude-science/runtime/<version>/agents/reviewer/metadata.yaml; reviewer permit set embedded in ~/.claude-science/bin/claude-science" note="Reviewer capability exclusions, trace rubric, and daemon-enforced read-only host surface" />.

The second rule is where the design shows its priorities: the reviewer weights a finding by where the claim lives. A wrong number in a saved figure or report is one the user cites next week with no transcript beside it, so artifacts are held to a strict bar. A loose phrase in chat scrolls away, so it is flagged only if acting on it would actually mislead. The reviewer guards the durable record, not the chatter.

These choices are measured, not asserted. The code that disables thinking notes that thinking cost about 72% of the reviewer's output tokens for roughly zero recall gain on trace-the-value work; the code that withholds Python notes that across thirty production reviewer rounds, Python was 41% of tool calls, all of it the recomputation the rubric forbids. ### It runs as detached windows, not a cron

Review does not fire on a clock. Immediately before the runner dispatches a batch of tool calls, it asks two things: has enough time passed since the last checkpoint, and has real work accumulated since. At the defaults that means at least 120 seconds plus one qualifying signal, three new artifacts, a structural Markdown block, or two thousand characters of authored input. Quiet waiting triggers nothing; activity without a qualifying signal triggers nothing <LocalSource id="verifier-config" source="Verifier configuration and runner predicate embedded in ~/.claude-science/bin/claude-science; extract with strings and search for 'min_checkpoint_interval_ms' and 'msSinceLastCheckpoint'" note="Verifier defaults and the pre-tool content-and-time checkpoint predicate" />.

When a checkpoint does fire, the verifier snapshots a bounded window, messages plus execution, artifact, plan, and provenance context, and dispatches a detached reviewer. If one is already busy, the new unit merges into the pending window; otherwise the hold timer lets nearby work coalesce first. ### Review can change control flow

The reviewer participates in flow control.

Natural completion passes through `_gateReviewerTerminalBarrier()`. The barrier decides whether the unreviewed tail needs a terminal checkpoint, flushes a held unit when appropriate, and waits for in-flight or pending review. It then drains review notices. If a notice should be delivered, the runner injects it into the session, increments a bounce counter, saves state, and returns a veto so the main agent must continue<LocalSource id="terminal-barrier" source="Runner code embedded in ~/.claude-science/bin/claude-science; search extracted strings for '_gateReviewerTerminalBarrier'" note="Terminal verification checkpoint, wait, notice drain, bounce, and completion veto" />. The idea is similar to how `/goal` or `/loop` is implemented in Claude Code and Codex.

The bounce count is bounded at three by default. This prevents the reviewer and main agent from trapping the session in an unlimited dispute.

The strongest case is a delegated result. When a sub-agent hands a structured output up to its parent and a reviewer fails it first, the runner throws the output away before the parent sees it and sends the sub-agent back to fix or rebut the finding and call `submit_output` again. The parent gets nothing until a corrected result comes back, or the retry budget runs out<LocalSource id="output-invalidation" source="Runner code embedded in ~/.claude-science/bin/claude-science; search extracted strings for 'outputInvalidationCount' and 'submit_output again'" note="Blocking finding and delegated structured-output invalidation" />. The reviewer can void a handoff between agents, not just flag it.

## Where do we go from here

Claude Science is not an AI that writes Python for scientists. It is a harness that puts AI, data, and compute under governance: code runs, but inside processes whose capabilities the daemon shapes; artifacts are produced, but as versioned records; review happens, but as flow control the daemon owns and can use to hold an answer back.

None of that is science-specific. A serious domain agent, in any field, is not built from a longer system prompt or a wider tool menu. It is built from the objects a harness makes durable and auditable, the boundaries it enforces between them, and the control flow it holds back for the moment the evidence disagrees with the agent.

Where will it go from here? Based on my observations of Claude Code, I would guess:

1. Anthropic will train or fine tune a Life Science vertical model, based on Opus or Fable.
2. Claude Science will reach v1.0 with a new model release. That model, vertical or not, will absorb a lot of knowledge from Claude Science usage, the way their recent models have absorbed knowledge from Claude Code.
3. Anthropic's own wet-lab initiatives will accelerate the coevolution of model, harness, and lab.

I look forward to seeing this product improve.
